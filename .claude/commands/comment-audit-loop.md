# 프로젝트 전체 주석 개선 + 코드 정합성 반복 검수 프롬프트

너는 이 프로젝트의 **주석 개선 오케스트레이터**다.

목표는 단순히 주석을 많이 추가하는 것이 아니다.
목표는 프로젝트 전체 코드를 기준으로, **사람이 읽기 좋은 주석**을 만들고, 그 주석이 실제 코드와 맞는지 반복 검증하는 것이다.

작업은 한 번에 끝내지 마라.
주석을 추가하거나 수정한 뒤에는 반드시 다시 코드를 읽고, 새 주석이 코드와 맞는지 검수하라.
틀린 주석, 과한 주석, 오래된 주석, 코드와 어긋난 설명이 있으면 다시 수정하고 다음 루프에서 재검수하라.

최종 완료 조건은 다음과 같다.

* 코드와 맞지 않는 주석 0건
* 오래되었거나 오해를 부르는 주석 0건
* 불필요하게 코드를 그대로 반복하는 주석 0건
* 주석 수정으로 인해 새로 생긴 혼란 0건
* 주석 개선 과정에서 발견된 실제 코드 버그 중 미처리 고위험 항목 0건
* 실행 가능한 테스트, 린트, 구문 검사 통과
* 더 이상 추가하거나 수정할 주석 후보가 없다고 여러 관점에서 확인됨

단, “진짜로 세상에 버그가 0개”라고 주장하지 마라.
완료 판단은 **현재 프로젝트 전체 검수 루프에서 새로 발견되는 문제가 0건**이라는 뜻으로만 사용하라.

## 2. 주석 작성 원칙

주석은 “코드를 한글로 번역한 문장”이 아니다.
주석은 코드만 봐서는 놓치기 쉬운 이유, 제약, 경계, 운영상 주의점을 설명해야 한다.

좋은 주석의 기준:

* 왜 이 처리가 필요한지 설명한다.
* 어떤 입력이나 상태를 전제로 하는지 밝힌다.
* 실패하거나 예외가 되는 조건을 적는다.
* 외부 시스템, 벤더, 장비, 스키마와의 계약을 설명한다.
* 이상해 보이는 코드가 왜 의도된 선택인지 설명한다.
* 유지보수자가 건드리면 안 되는 경계를 알려준다.
* 코드와 가까운 위치에 짧게 둔다.

나쁜 주석의 기준:

* 코드가 이미 말하는 내용을 그대로 반복한다.
* “효율적으로”, “안정적으로”, “체계적으로” 같은 추상어로 뭉갠다.
* 실제 코드에는 없는 동작을 설명한다.
* 과거 구현 기준의 낡은 설명을 남긴다.
* TODO만 있고 조건, 이유, 후속 기준이 없다.
* 장황해서 코드를 읽는 흐름을 막는다.
* AI가 쓴 것처럼 과하게 반듯하고 일반론적이다.

예시:

나쁨:

```python
# 리스트를 순회하면서 값을 추가한다.
```

좋음:

```python
# Redfish 응답은 벤더별로 단일 객체와 배열이 섞여 들어온다.
# 이후 정규화 단계가 list만 받기 때문에 여기서 형태를 먼저 맞춘다.
```

나쁨:

```yaml
# 데이터를 효율적으로 수집한다.
```

좋음:

```yaml
# raw fallback은 Python facts가 실패한 장비에서도 최소 하드웨어 정보를 남기기 위한 경로다.
```

## 3. 주석 언어와 톤

기존 파일의 주석 언어를 우선 따른다.

* 기존 주석이 한국어면 한국어로 쓴다.
* 기존 주석이 영어면 영어로 쓴다.
* 파일 안에 언어가 섞여 있으면 주변 주석과 같은 언어를 쓴다.
* 공개 라이브러리 성격의 Python docstring은 영어가 더 자연스러우면 영어로 유지한다.
* 운영 문맥, 장애 대응, Jenkins, Ansible task 설명은 한국어가 더 명확하면 한국어로 쓴다.

톤은 담백하게 쓴다.

금지:

* 과장
* 홍보 문장
* 감정 표현
* AI식 일반론
* “이 코드는 매우 중요합니다” 같은 빈 강조
* 특수문자 장식
* 이모지
* 의미 없는 굵은 글씨
* 중간점 남발

## 4. 주석을 추가할 곳

프로젝트 전체를 훑고 아래 위치를 우선 점검하라.

1. Python

   * 복잡한 함수
   * 외부 응답 파싱
   * 벤더별 분기
   * 예외 처리
   * fallback 처리
   * 스키마 변환
   * 암묵적인 입력 계약
   * 테스트가 의도를 보완하지 못하는 부분

2. Ansible YAML

   * `block/rescue/always`
   * `set_fact`로 fragment를 만드는 부분
   * `include_tasks`의 순서가 중요한 부분
   * 실패해도 계속 진행하는 부분
   * 벤더별 조건 분기
   * OUTPUT 직전 조립 단계
   * vault, inventory, callback 관련 제약

3. Jenkinsfile

   * stage 순서
   * fail gate
   * artifact, console output, callback 의존성
   * dry-run과 실제 실행 차이

4. Schema / adapters

   * 필드 의미가 헷갈리는 부분
   * Must/Nice/Skip 판단 기준
   * 벤더별 match 조건
   * priority와 specificity 계산에 영향을 주는 부분

5. Tests

   * fixture가 실제 장비인지 mock인지 구분해야 하는 부분
   * baseline이 계약처럼 쓰이는 부분
   * 회귀 테스트가 보호하는 동작

---

## 5. 주석을 추가하지 말아야 할 곳

다음 경우에는 주석을 추가하지 마라.

* 변수명과 함수명만으로 충분히 이해되는 코드
* 단순 import
* 단순 할당
* 단순 반복문
* 명백한 조건문
* 이미 테스트 이름이 의도를 잘 설명하는 경우
* 문서에 충분히 설명되어 있고 코드 가까이에 중복 설명이 필요 없는 경우
* 주석이 없어서 문제가 아니라 코드 이름이 나빠서 문제인 경우

코드 이름이 문제라면 주석으로 덮지 말고, 리팩터링 후보로 기록하라.
단, 이름 변경은 영향도가 크므로 테스트와 검색으로 안전성을 확인한 뒤에만 적용하라.

## 6. 멀티에이전트 역할 분담

가능하면 다음 역할을 나누어 병렬 또는 순차로 수행하라.

### A. Comment Mapper

프로젝트 전체에서 기존 주석, docstring, Ansible task name, README와 코드 설명을 수집한다.

산출물:

* 주석이 많은 파일
* 주석이 부족한 파일
* 오래된 주석 후보
* 코드와 맞는지 확인이 필요한 주석 후보
* 주석 없이 읽기 어려운 복잡한 코드 후보

### B. Code Truth Reviewer

주석을 믿지 말고 코드를 기준으로 사실을 검증한다.

검증 기준:

* 주석의 설명이 실제 분기와 맞는가
* 입력, 출력, 예외, fallback 설명이 맞는가
* 벤더별 동작 설명이 코드와 맞는가
* 테스트 fixture와 baseline 설명이 실제 파일과 맞는가
* README·docs/ 의 설명과 코드가 충돌하지 않는가

### C. Human Comment Writer

주석을 사람이 읽기 좋게 고친다.

작성 기준:

* 짧게
* 코드 가까이에
* 이유 중심으로
* 운영 제약 중심으로
* 추상어 금지
* 코드 반복 금지
* 확실하지 않은 내용은 쓰지 않기

### D. Bug Finder

주석 검수 중 발견한 실제 코드 문제를 따로 분류한다.

분류:

* 실제 버그
* 잠재 버그
* 테스트 부족
* 문서 불일치
* 이름 문제
* 구조 개선 후보

주석 개선 작업 중 실제 버그를 발견하면 무시하지 마라.
수정 가능한 버그는 테스트와 함께 고쳐라.
큰 설계 변경이 필요한 버그는 별도 이슈로 분리하고, 이번 작업에서 건드릴지 판단 근거를 남겨라.

### E. Regression Tester

수정 후 실행 가능한 검증을 수행한다.

우선순위:

1. Python syntax check
2. pytest
3. Ansible syntax-check
4. Jenkinsfile 정적 확인
5. schema validation
6. baseline regression
7. 변경 파일 중심 smoke test

실행할 수 없는 검증은 “실행 불가”로 표시하고 이유를 남겨라.
실행하지 않았는데 통과했다고 말하지 마라.

### F. Cross Reviewer

다른 에이전트가 수정한 주석을 다시 검토한다.

검토 기준:

* 새 주석이 코드와 맞는가
* 새 주석이 너무 많지 않은가
* 주석 때문에 오히려 이해가 어려워졌는가
* 같은 설명이 여러 곳에 중복되지 않았는가
* 수정 중 실제 동작이 바뀌지 않았는가
* 테스트가 필요한 변경이 테스트 없이 들어가지 않았는가

## 7. 반복 루프

반드시 아래 루프를 반복하라.

### Loop 0. 기준선 수집

* 현재 테스트 상태 확인
* 현재 주석 상태 확인
* 주요 문서와 코드의 불일치 후보 수집
* 변경 전 문제 목록 작성

### Loop 1. 첫 번째 수정

* 오래된 주석 제거
* 틀린 주석 수정
* 필요한 주석 추가
* 너무 뻔한 주석 삭제
* 주석으로 덮고 있던 코드 냄새 기록

수정 후 바로 완료하지 마라.

### Loop 2. 코드 기준 재검수

방금 수정한 주석을 다시 코드와 대조하라.

각 주석마다 다음 질문을 던져라.

* 이 설명은 현재 코드 기준으로 사실인가?
* 예외 경로까지 맞는가?
* 테스트 fixture와도 맞는가?
* 벤더별 차이를 뭉개지 않았는가?
* “항상”, “절대”, “보장” 같은 단어가 실제로 보장되는가?
* 이 주석이 없어도 코드만으로 충분하지 않은가?

틀린 주석은 즉시 고쳐라.

### Loop 3. 새 문제 탐색

기존에 고친 문제만 보지 마라.
프로젝트 전체에서 새로 남은 문제를 다시 찾아라.

찾을 것:

* 새로 생긴 중복 설명
* 주석과 문서의 충돌
* 코드 이름과 주석의 불일치
* 테스트 설명과 실제 fixture의 불일치
* 코드 변경 없이 주석만 바꿨는데 의미가 달라진 부분
* 주석 개선 과정에서 드러난 실제 버그

### Loop 4. 재수정

Loop 2와 Loop 3에서 발견한 문제를 수정한다.

수정 후 다시 Loop 2로 돌아간다.

### Loop N. 종료 판단

다음 조건을 모두 만족할 때만 종료하라.

* 이번 루프에서 새로 발견된 주석 문제 0건
* 이번 루프에서 새로 발견된 코드 버그 0건
* 이번 루프에서 새로 발견된 문서 불일치 0건
* 변경 파일 전체 재검수 완료
* 프로젝트 전체 샘플링 재검수 완료
* 실행 가능한 검증 통과
* 미실행 검증은 이유와 위험도를 명시

한 에이전트가 “완료”라고 판단해도 끝내지 마라.
반드시 다른 에이전트가 최종 반박 검토를 수행해야 한다.

## 8. 실제 코드 변경 규칙

주석만 고치는 작업이 원칙이다.

하지만 주석 검수 중 실제 코드 버그가 발견되면 다음 기준으로 처리하라.

### 바로 수정 가능

다음 조건을 모두 만족하면 코드도 수정해도 된다.

* 버그 원인이 명확하다.
* 수정 범위가 작다.
* 테스트를 추가하거나 기존 테스트로 검증 가능하다.
* schema, OUTPUT, inventory, vault 계약을 깨지 않는다.
* 회귀 위험이 낮다.

### 별도 이슈로 분리

다음 경우에는 주석 작업에서 직접 고치지 말고 이슈로 남긴다.

* 설계 변경이 필요하다.
* 벤더별 영향이 크다.
* baseline 교체가 필요하다.
* 실장비 검증이 필요하다.
* schema 계약 변경 가능성이 있다.
* Jenkins 운영 방식에 영향이 있다.

이슈로 분리할 때는 다음 형식으로 남겨라.

```text
[Deferred Issue]
- 위치:
- 발견 경로:
- 문제:
- 영향:
- 왜 이번 작업에서 직접 고치지 않는가:
- 필요한 검증:
```

## 9. 검증 명령 후보

프로젝트에 맞춰 실제 존재하는 명령만 실행하라.
없는 명령을 만들어내지 마라.

가능하면 다음을 확인하라.

```bash
python -m compileall .
pytest
ansible-playbook --syntax-check os-gather/site.yml
ansible-playbook --syntax-check esxi-gather/site.yml
ansible-playbook --syntax-check redfish-gather/site.yml
python tests/validate_field_dictionary.py
```

프로젝트에 별도 테스트 스크립트나 Makefile, tox, nox, Jenkins dry-run 문서가 있으면 그쪽을 우선한다.

검증 결과는 반드시 실제 실행 결과 기준으로 적어라.
실행하지 않은 항목은 “미실행”이라고 적어라.

## 10. 보고 형식

각 루프가 끝날 때마다 아래 형식으로 보고하라.

## 11. 엄격한 금지 사항

다음은 하지 마라.

* 코드를 읽지 않고 주석을 상상해서 추가
* 주석으로 코드 버그를 숨기기
* 오래된 주석을 보존하려고 억지 해석하기
* 테스트를 실행하지 않고 통과했다고 말하기
* “전체 문제 0개”라고 과장하기
* 수정한 주석을 재검수하지 않고 완료하기
* 한 번 발견한 버그만 고치고 프로젝트 전체 재탐색을 생략하기
* 기존 출력 스키마, inventory 계약, OUTPUT 태스크명, vault 로딩 구조를 임의 변경하기
* 큰 리팩터링을 주석 개선 작업에 몰래 끼워 넣기
* 불확실한 내용을 사실처럼 주석에 쓰기

## 12. 최종 목표

주석은 코드 옆의 작은 운영 문서다.

읽는 사람이 다음을 바로 알 수 있어야 한다.

* 이 코드가 왜 있는지
* 어디까지가 의도된 동작인지
* 어떤 입력과 외부 계약을 전제로 하는지
* 어떤 예외를 일부러 허용했는지
* 어디를 건드리면 위험한지
* 테스트가 무엇을 보호하는지

위 기준을 만족할 때까지 수정, 재검수, 새 문제 탐색을 반복하라.
더 이상 추가하거나 수정할 주석 후보가 0건이고, 새로 발견되는 불일치와 버그가 0건일 때만 완료로 판단하라.
